# 迭代 docs 文档（iterate-docs）

根据**最新改动的代码**，完善并迭代 `docs/` 下的专题文档，使文档始终与真实代码行为一致。本 Skill **不负责 README.md**（README 由其它流程维护），只聚焦于 `docs/` 目录。

## 定位与边界

- **输入**：代码改动（工作区 diff / 近期提交 / 用户指定的改动范围）。
- **输出**：`docs/` 下相关文档的增量更新。
- **不负责**：`README.md`、代码本身、自动 git 提交。
- **真相源原则**：代码是真相源，文档跟着代码走；只根据真实代码更新文档，不臆造代码行为、不把文档旧描述反向写回代码。
- **纯前端约束**（继承 AGENTS.md）：文档示例不得出现对接后端、真实登录、真实权限（roles / 动态路由接真接口）、真实数据库的内容；登录 / 权限 / 数据一律以 mock 演示。

## 触发场景

- 用户说："同步文档" / "docs 迭代" / "扫描代码更新 docs" / "代码改了更新文档" / "把刚改的代码补进文档"
- 项目新增 / 变更了工程化配置、UI、路由、请求层、构建策略等，需要让 `docs/` 对应章节同步
- 用户显式调用本 Skill

## 第一步：确定改动范围（扫描最新代码）

按以下优先级确定"新改动的代码"：

1. **工作区改动（优先）**：
   - `git status --short` 看是否有未提交改动；
   - 有则 `git diff HEAD --stat` + 必要时 `git diff HEAD <具体文件>` 取得改动集合，作为本次迭代依据。
2. **工作树干净时**：
   - `git log --oneline -15` 列出近期提交；
   - 与用户确认要覆盖的提交范围（默认取最新一条），用 `git diff <base>...HEAD` 取得改动；或
   - 若用户只是想"整体校对一遍"，进入"漂移扫描"模式：直接读取映射到的源码模块，与文档逐段比对差异（见第三步）。
3. **用户显式指定范围**：如"只看了构建相关的改动"，则以用户给定文件 / 目录为准。

## 第二步：代码 ↔ 文档 映射

**2.0 文档清单核对（运行时，防映射表过期）**：`docs/` 会持续增多，下方映射表只是「已知锚点种子」，**不能假定它封闭或永远正确**。每次执行先做一次核对：

1. `find docs -name '*.md'` 列出当前**全部**文档（不只表里的那些）；
2. 校验映射表里写的目标路径是否都还存在——不存在则标 `stale`，提示「映射目标 X 已不存在，请确认文档是否已改名 / 迁移」；
3. 把全部文档名按目录分组列出，作为后续「未覆盖改动」的候选归属池；
4. 映射表未命中某次改动时，从文档目录名 / 标题关键词推断归属，或放进方案让你人工指定。

> 目的：文档再怎么涨，本 Skill 也不会 silently 漏更或指向死路径；映射表只用于加速命中，不卡正确性。

将改动文件按下列映射定位受影响的文档章节（一个文件可能映射到多篇文档）：

| 代码改动落点 | 应更新的文档 |
| --- | --- |
| `src/styles/**`、`uno.config.ts`、`public/css/**` | `docs/前端工程化.md`「六、样式与 UI」+ `docs/UI组件/SvgIcon图标.md` |
| `src/assets/svg-icons/**`、`scripts/svg-clean.ts` | `docs/UI组件/SvgIcon图标.md` |

| `src/store/**`、`src/router/**` | `docs/前端工程化.md`「四、状态与路由」 |

## 第三步：读取与核对（漂移检测）

对映射到的每篇文档：
1. 只读读取文档现状 + 对应改动代码；
2. 逐段核对，标记差异类型：
   - **路径 / 文件名过时**（如文档写 `src/xxx.ts` 但已迁移）；
   - **配置片段过期**（如 plugin 选项、uno 规则、EP 主题变量与代码不符）；
   - **能力缺失**（代码新增了能力但文档未提）；
   - **行为描述错误**（文档说的逻辑与代码实现不一致）；
   - **冗余**（代码已删除的能力仍在文档里）。

## 第四步：自检硬约束

落笔前逐条核对：
- 中文为主，技术关键词（Vue / TypeScript / Vite / Pinia / UnoCSS / Element Plus / gzip 等）保留英文；
- 文档中的代码示例遵守 `AGENTS.md`：图标统一用 `<SvgIcon>`（不引 `@element-plus/icons-vue`、不内联裸 svg）；工具方法统一从 `@/utils` barrel 引入；
- 纯前端，不引入后端 / 真实登录 / 真实权限 / 真实数据库；
- 只基于真实代码更新，不杜撰章节或收益数据；
- 保持各文档既有「配置详解 / 为什么这么做」的基调与章节结构。

## 第五步：先出方案（不立即改文件）

把差异整理成**具体改动清单**，回给用户确认：

```
文档：docs/构建与工程化/构建文件拆分.md
- 段落：「vendor 分包」小节
- 旧：(摘录旧描述)
- 新：(建议改后的描述，可附真实代码片段)
- 为什么：vite.config.ts 已新增 x 分包规则，文档未同步
```

> 多文档改动时，按文档分组列出；每条都给出"旧 → 新 → 为什么"，便于用户判断。

## 第六步：等确认

- 用户明确说"落地 / 执行 / 开始"后再编辑文件；
- 否则只给方案，不改动任何文件。

## 第七步：落地改动

按确认清单编辑对应文档：
- 使用 Edit 工具做精准替换，尽量只动差异段落，不重写整篇；
- 只动与本次改动相关的文档；若确属新增能力，在对应文档合适位置补段落，不破坏现有结构；
- 同步更新 `docs/前端工程化.md` 总纲（如能力域增删）；
- 保持术语、语气与现有文档一致。

## 第八步：二次核验 + 小结

1. 复读改动段落，确认与代码一致、无遗留过时描述；
2. 确认未误伤无关章节；
3. 输出小结：改了哪些文档 / 段落、是否同步了总纲、有无需用户手动处理的遗留项（如 README 同步——本 Skill 不负责 README）。

## 约束

- 不自动 `git commit`；
- 不改代码、不动 `README.md`、不扩写与本次改动无关的文档；
- 所有写操作（编辑文档）必须用户确认，绝不自动执行；
- 文档跟着代码走：以代码为真相源，不反向修改代码去迁就文档。

## 风险与注意

- **代码是真相源**：文档描述必须与代码实现一致；发现代码与文档冲突时，更新文档，而非暗示"代码应该改"。
- **映射遗漏**：映射表未覆盖的改动，需人工判断归入哪篇文档；不确定时把候选文档都列入方案让用户选。
- **结构一致性**：`docs/前端工程化.md` 是总纲，子文档是展开；以总纲章节为纲，子文档补充细节，不要反向把子文档的措辞写回总纲造成口径冲突。
- **README 不在范围**：本 Skill 只管 `docs/`；README 的同步请用其它流程，不要在本 Skill 内顺手改 README。

## 验证

- 改动文档中，被更新的段落所述路径 / 配置 / 行为与 `git diff` 或当前代码一致；
- 映射到的每篇文档都已覆盖，无"改了代码却漏更文档"；
- 未改动与本次代码无关的文档章节；
- 文档示例符合 `AGENTS.md`（SvgIcon、@/utils barrel、纯前端）。

# git-commit-msg

## 触发语
用户说「提交代码」或等价表达时触发。

## 流程

### 第一步：生成候选 message
1. 先查看真实改动：`git status -s` + `git diff HEAD --stat`
2. 基于改动生成 **5 条彼此有差异的单行中文候选 message**，格式：`<type>: <简述>`
   - 中文动词开头，≤50 字，无句号
   - **每条候选都必须全面覆盖本次全部改动**（所有改动文件 / 主题都要在简述中体现），禁止只描述改动的一部分
   - 候选之间的「差异」应体现在 **type 选择**（fix / feat / refactor / chore / perf 等）与**措辞角度**，而**不是**把改动割裂成几条各讲一半
   - 若本次存在多个独立主题（如同时有「A 功能」与「B 修复」），每条候选都需**同时提及 A 与 B**，仅侧重点 / 归纳方式不同
   - 候选超过 4 条时必须用**纯文本**列出 1-5，不能用快捷组件
3. 列出候选，等待用户回复编号（1-5）

常用 type：`build` / `chore` / `perf` / `refactor` / `feat` / `fix` / `docs` / `test` / `style` / `ci`

### 第二步：最终提交前强制自检（关键约束）
**在用户选定 message 后、执行 git add 前，必须执行本自检，不可跳过。**
1. 执行 `git status --short`
2. 若输出为空 → 停止，告知用户「当前无改动可提交」
3. 若输出非空 → 列出所有未提交文件，**重点检查 `.workbuddy/` 是否有改动**
4. `.workbuddy/` 目录下的所有改动**必须一并纳入本次提交**，禁止单列、禁止询问用户「是否一起提交」
5. 提示用户本次将提交的文件清单与选定 message，等待用户最终确认
6. 用户确认后，使用**最新** `git status --short` 的结果进行 `git add`（优先 `git add -A` 或按列出的文件 add），然后 `git commit -m "<message>"`

### 原则
- 所有写操作（add / commit）必须用户确认，绝不自动执行
- **本技能只提交到本地暂存区，不推送远程**：沙箱环境无 TTY，GCM 推送常报 `could not read Username`（即使偶尔实际成功，报错也易造成混淆）；如需推送到远程，由用户在自有终端执行 `git push`
- 不要基于过时的文件列表 add；每次 add 前必须以最新的 `git status --short` 为准
- 提交后不再追加编辑 `.workbuddy/memory/*.md` 等文件，避免再次产生脏数据；如需追加，必须再提交

## 历史纠偏
- 此前曾误记为「只输出不擅自 commit」而直接 commit，已纠正：必须 5 候选 + 最终确认 + 提交前自检。
- 候选 message 曾把「有差异」误解为「各讲一部分」，导致每条只覆盖一半改动；已纠正：差异只体现在 type 与措辞角度，**每条都必须完整概括本次全部改动**，多个主题要并列点齐。
- 2026-07-27：移除「确认提交方式 / 提交并推送」环节。原因：推送在本环境频繁因 TTY/GCM 凭证问题报 `could not read Username`。改为「选定 message → 提交前自检 → 直接本地提交」，推送交回用户本地终端。流程由「5 候选 → 确认方式(含推送) → 自检 → 提交」简化为「5 候选 → 自检 → 本地提交」。

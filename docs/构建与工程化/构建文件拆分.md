# 构建文件拆分

## 功能定位

构建期对产物做**分包（chunk splitting）**：把稳定的第三方库从业务代码里拆成独立、带 hash 的 chunk。本文只谈「拆成哪些块、怎么命名、为什么要拆」，不涉及传输压缩、调试语句剔除等其他构建优化。

## 实现要点

| 落地点 | 职责 |
| --- | --- |
| `vite.config.ts` `build.rolldownOptions.output.codeSplitting.groups` | vendor 分包核心；按正则把 `vue/pinia/vue-router/axios/dayjs` 各自归入独立 chunk，`priority` 由高到低（16→12），数值大者优先命中、避免被更宽松规则吞掉 |
| `vite.config.ts` `build.rolldownOptions.output.chunkFileNames` / `entryFileNames` | 统一命名规则 `js/[name]-[hash].js`，`[hash]` 保证内容变化才换名、未变则命中缓存 |
| `vite.config.ts` `build.cssCodeSplit: true` | CSS 按需拆分，每个入口/异步块产出自用样式而非整包一团 |

### 机制

Rolldown 在打包时按 `codeSplitting.groups` 的正则扫描模块路径：
- 命中 `node_modules/(vue|@vue)/` → 归入 `vue` chunk；其余库同理各归其位；
- 业务代码不匹配任何 group → 留在入口/路由懒加载块中；
- 每个 chunk 文件名带内容 hash，内容不变则文件名不变。

结果目录（`dist/js/`）形如：`vue-<hash>.js`、`pinia-<hash>.js`、`vue-router-<hash>.js`、`axios-<hash>.js`、`dayjs-<hash>.js` + 业务入口块。

## 好处

- **利用浏览器缓存机制（核心收益）**：第三方库内容随发版极少变动，拆成独立 chunk 后其文件名 hash 长期稳定；hash 不变 → 文件名不变 → 浏览器强缓存长期命中，**二次访问免重下**。业务发版只动业务块，vendor 块纹丝不动、不会因整体重打包而被迫失效。
- **减小用户侧有效传输体积**：因 vendor 被长效缓存，老用户回访只需拉取变更的业务块，长期累计下载量显著下降；不必在首屏一次性下完整个大包。
- **首屏多块并行下载**：单一大 bundle 拆成多个小块，浏览器可并行拉取（HTTP/2 多路复用），缓解单文件下载阻塞，首屏更快可见。
- **首屏按需加载（路由级代码分割）**：拆分使路由级 `() => import()` 各自成块，首屏只下载当前路由所需块，未访问页面的代码不进首屏包，进一步压低首屏负载。
- **单块体积可控，降低主线程解析阻塞**：避免把全部代码压成单一超大文件；单块体积收敛后，浏览器解析/编译的单次主线程占用更短，减少长任务卡顿。
- **变更影响范围收窄（精准失效）**：某库升级只改变对应块的内容 hash，仅该块文件名变化、需重新下载，其他 vendor 块与业务块不受影响，失效粒度最小化。
- **可精细控制加载优先级**：离散的块可对关键块做 `modulepreload`、对非关键块做 `prefetch`，按需调度加载顺序，而非一整包被动等待。
- **命名块便于定位（开发体验）**：`[name]` 命名让每块在 DevTools / Network 面板中直接看出归属（vue / pinia / 某路由），排查体积与加载问题更快。

## 工程化好处

- **关注点分离**：vendor 与 app 解耦，缓存策略、体积治理可分别施策。
- **可维护**：新增需要独立分包的稳定库，只需在 `groups` 加一条 `name + test + priority`，不动其他配置。
- **可复制标准范式**：Rolldown/Rollup 的 manual chunks 是业界通用做法，新人照此即可治理任意项目产物。

## 注意事项

- **`priority` 数值大者优先**：`vue` 取最高 16，确保它被精确规则捕获、不被更宽泛的 group 误吞；新增 group 时注意优先级排布。
- **仅拆「稳定且通用」的库**：业务代码仍走路由级 `() => import()` 懒加载，不与本处分包混为一谈（两者作用层级不同）。
- **`[hash]` 在文件名是关键**：移除 hash 会导致缓存无法失效、旧代码被复用，切勿为「文件名好看」而改用无 hash 命名。

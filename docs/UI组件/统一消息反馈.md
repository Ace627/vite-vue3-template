# 统一消息反馈（TipModal）

## 功能定位

把 Element Plus 的四类反馈 API——`ElMessage`（轻提示）/ `ElMessageBox`（弹窗、确认、输入）/ `ElNotification`（通知）/ `ElLoading`（遮罩）——收口到 `src/utils/tip-modal.ts` 的 `TipModal` 抽象类。全项目**只从 `@/utils` 引入 `TipModal`**，杜绝散装 `import { ElMessage } from 'element-plus'`；统一标题「系统提示」、统一按钮文案（知道了 / 确定 / 取消）、`confirm`/`prompt` 用返回值替代 `try-catch`。它是项目统一的「用户反馈层」。

## 实现要点

| 方法 | 底层 API | 说明 |
| --- | --- | --- |
| `TipModal.msg` / `msgError` / `msgSuccess` / `msgWarning` | `ElMessage` | 轻提示四态；固定 `plain: true` 样式 |
| `TipModal.alert` / `alertError` / `alertSuccess` / `alertWarning` | `ElMessageBox.alert` | 弹窗四态；固定标题「系统提示」、`showClose:false`、按钮「知道了」 |
| `TipModal.confirm(content)` | `ElMessageBox.confirm` | 确认窗；返回 `Promise<{ confirm: boolean; cancel: boolean }>`，`cancel` 由 reject 归一、调用方免 `try-catch` |
| `TipModal.prompt(content)` | `ElMessageBox.prompt` | 输入窗；返回 `{ confirm, cancel, value }` |
| `TipModal.notify` / `notifyError` / `notifySuccess` / `notifyWarning` | `ElNotification` | 通知四态；固定标题「系统提示」 |
| `TipModal.showLoading` / `hideLoading` | `ElLoading.service` | 遮罩；模块级 `loadingInstance` 单例，`showLoading` 复用同一实例、`hideLoading` 关它 |

### 机制

- **统一话术**：`alert*` 固定标题「系统提示」+ `showClose:false` + 按钮「知道了」；`confirm`/`prompt` 固定「确定 / 取消」。
- **错误归一**：`confirm`/`prompt` 内部 `try/catch` 把 `ElMessageBox` 的 reject 转成 `{ confirm:false, cancel:true }`（prompt 附 `value:''`），调用方不用 `try-catch` 也能拿到结构化结果。
- **loading 单例**：模块级 `let loadingInstance` 仅一份，`showLoading` 复用同一实例（多次调用不叠多层遮罩），`hideLoading` 关它。
- **barrel 出口**：`src/utils/index.ts` 统一 re-export，业务侧只 `import { TipModal } from '@/utils'`。

## 好处

- **单一入口、禁止散装 import（核心收益）**：全项目反馈只走 `TipModal`，呼应 AGENTS.md 的 `@/utils` 唯一入口红线；不会出现「有人用 `ElMessage`、有人用 `TipModal.msg`」的分裂。
- **统一视觉与话术**：标题「系统提示」、按钮「知道了 / 确定 / 取消」全站一致，体验统一、不各写各的。
- **`confirm`/`prompt` 返回结构化结果，免 `try-catch`**：reject 归一为 `{ cancel:true }`，调用方用 `if (res.confirm)` 平铺处理，错误流更清晰、不易漏 catch。
- **类型安全**：入参标注 `MessageOptions` / `ElMessageBoxOptions` / `NotificationOptions`，IDE 补全与校验到位。
- **反馈行为可集中治理**：要改默认样式、加埋点、统一超时，只动 `tip-modal.ts` 一处，不必逐处改调用。
- **与按需引入解耦**：函数式 API 样式由 `unplugin-element-plus` 注入（曾误删致 `ElMessage` 样式丢失，已恢复），封装层不关心样式机制，只管调用。
- **loading 单例防叠加**：多次 `showLoading` 不堆多层遮罩，`hideLoading` 一次清空，避免遮罩关不掉的经典 bug。
- **全局复用**：请求错误拦截（`response-error.ts`）、登录（`login.vue`）、设置（`setting.ts`）都已复用同一层，无重复实现。
- **缩写调用**：`TipModal.msgError(x)` 一行，对比手写 `ElMessage({ type:'error', message:x, plain:true })` 更短。
- **替换成本低**：将来换反馈库（或自绘），只改 `tip-modal.ts` 一层，业务无感。
- **可复制标准实践**：此类「反馈收口」是工程化通用范式，新项目直接搬该类即可。

## 工程化好处

- **关注点分离**：反馈逻辑集中在 `tip-modal.ts`，与业务组件解耦。
- **约束即文档**：barrel 强制统一入口，与 AGENTS.md「复用 `@/utils`、统一从 `@/utils` 导入」红线一致。
- **可维护**：新增反馈类型（如 `msgInfo`）只加一个 `static` 方法，不动调用方。
- **可复制范式**：收口函数式 API 是前端工程化基础设施标配，新人照此即可统一项目反馈。
- **与 AGENTS.md 单一入口红线一致**：所有反馈走 `@/utils` 出口，无散装 EP import。

## 注意事项

- **函数式 API 样式靠 `unplugin-element-plus` 注入**：`ElMessage` 等从 `'element-plus'` 显式 import 的函数，其样式 resolver 不会自动注入，必须靠 `unplugin-element-plus({ useSource:true })`；曾误删该插件致 `ElMessage` 样式丢失（已恢复）。
- **`plain` 样式与 `type` 默认值**：`msg*` 固定 `plain:true`；覆盖时传 `config` 即可，但注意不破坏统一观感。
- **`confirm`/`prompt` 的 `cancel` 由 reject 归一**：调用方务必用返回值判断，不要外层再包 `try/catch`（会重复处理）。
- **loading 单例须配对 `hideLoading`**：`showLoading` 后必须对应 `hideLoading`，否则遮罩不消；异常分支也要确保关遮罩。
- **TS `erasableSyntaxOnly` 下抽象类仅类型层**：`abstract class TipModal` 编译后无运行时实体（不被实例化），仅作静态方法命名空间，无额外体积。
- **不要绕过封装直引 `ElMessage`**：会破坏统一入口红线与样式一致性，务必走 `TipModal`。
